# Приоритетное вытеснение подов и автоскейлинг нод в Kubernetes: PriorityClass, Cluster Autoscaler и «тёплый» резерв через placeholder-поды

Задача, знакомая многим командам: в кластере Kubernetes живут критически важные сервисы, а рядом с ними — «специализированные» нагрузки: batch-обработка, CI-раннеры, ML-эксперименты, фоновые расчёты. Когда ресурсов не хватает, обычно выбирают между двумя плохими вариантами: держать статический пул нод, которые ночью простаивают и стоят денег, или положиться на cluster autoscaling — и тогда бизнес-поды проведут в статусе Pending 3-5 минут, пока автоскейлер развернёт новую ноду.

В Kubernetes это стандартный паттерн, который настраивается через PriorityClass и механизмы Cluster Autoscaler. Когда кластеру не хватает ресурсов, поды с низким приоритетом вытесняются (evicted), уступая место подам с высоким приоритетом. Вытесненные поды переходят в статус Pending, что автоматически заставляет Cluster Autoscaler создавать новую ноду. Кластер сам решает, кому жить на дорогих вычислительных мощностях, а кому подождать.

Мы разберём два применения этой механики. Первое — честное: пускать «специализированные» нагрузки на остатках кластера, зная, что при дефиците их вытеснят, а автоскейлер развернёт им новую ноду. Второе — изящный трюк [overprovisioning](https://kubernetes.io/docs/tasks/administer-cluster/node-overprovisioning/): заполнить часть кластера ничего не делающими placeholder-подами, чтобы ноды под будущий пик создавались заранее, а место для критичных сервисов освобождалось за секунды, а не минуты.

В этой статье разберём, как это устроено внутри, и развернём полный демо-стенд в Yandex Managed Kubernetes: от Terraform-кластера с автоскейлингом до живого вытеснения подов, которое можно наблюдать своими глазами в `kubectl get events`.

## Как это работает: три механизма в связке

Прежде чем идти к практике, важно понять, что приоритетное вытеснение — это не одна фича, а результат работы трёх компонентов Kubernetes, которые существуют независимо друг от друга:

**1. Приоритет пода (PriorityClass).** Каждый под получает числовое значение приоритета — напрямую или через PriorityClass. Это число хранится в `pod.spec.priority` и учитывается в двух местах: планировщиком при выборе жертвы вытеснения и kubelet при eviction под давлением ресурсов.

**2. Вытеснение (Preemption).** Когда высокоприоритетный под не может разместиться, планировщик Kubernetes не просто оставляет его в Pending — он ищет ноды, где сумма приоритетов работающих подов ниже, чем у кандидата. Если удаляя один или несколько низкоприоритетных подов планировщик освобождает достаточно ресурсов — он их вытесняет. Важный нюанс: планировщик сравнивает приоритеты только тогда, когда физически не может разместить под из-за нехватки запрошенных ресурсов (`resources.requests`). Без корректно выставленных requests вся эта механика не работает.

**3. Автоскейлинг нод (Cluster Autoscaler).** Вытеснённый под — особенно если вытеснять больше некого — переходит в статус Pending. Cluster Autoscaler видит поды, которые не могут разместиться, и разворачивает новую ноду. Спустя 2–3 минуты (типичное время создания ноды в облаке) под запускается на ней.

Получается замкнутый цикл: **нехватка ресурсов → вытеснение низкоприоритетных → Pending → новая нода → вытеснённые поды запускаются на ней**. Кластер переживает пиковые нагрузки без ручного вмешательства.

```
        высокая нагрузка
              │
              ▼
   ┌─────────────────────┐
   │ critical-app        │ priority 1000000
   │ не помещается       │──────────┐
   └─────────────────────┘          │
                                    ▼
                     планировщик: у кого приоритет ниже?
                                    │
              ┌─────────────────────┴──────────────┐
              ▼                                    ▼
   ┌─────────────────────┐            ┌─────────────────────┐
   │ specialized-worker  │ evicted    │  Cluster Autoscaler │
   │ priority 1000       │───────────►│  новая нода         │
   │ → Pending           │            │  → worker запущен   │
   └─────────────────────┘            └─────────────────────┘
```

## Как это настроить

Настройка состоит из трёх шагов: два PriorityClass (дефолтный высокий и явный низкий), назначение низкого класса специализированным подам и включённый автоскейлинг нод.

### Шаг 1. Создайте PriorityClass по умолчанию

Сделайте так, чтобы все обычные поды в кластере автоматически получали высокий приоритет:

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority-default
value: 1000000
globalDefault: true # Все поды без указанного priorityClassName получат этот класс
description: "Приоритет по умолчанию для всех обычных подов"
```

Ключевое поле здесь — `globalDefault: true`. Приоритет из этого класса автоматически присваивается каждому поду, в манифесте которого не указан `priorityClassName`. Это защищает вас от ситуации, когда какой-нибудь системный под или свежедеплойнутый сервис остался без приоритета и стал невольной жертвой вытеснения.

> Важно: `globalDefault` должен быть только у одного PriorityClass в кластере. И обратите внимание — при создании кластера Kubernetes уже создаёт PriorityClass `system-cluster-critical` (значение 2000000000) для системных подов, поэтому значение 1000000 для дефолтного класса — безопасный выбор.

### Шаг 2. Создайте PriorityClass для специализированных подов

Для специализированных подов создайте класс с более низким значением:

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: low-priority-specialized
value: 1000 # Меньше, чем у дефолтного класса
globalDefault: false
description: "Низкий приоритет для специализированных подов"
```

### Шаг 3. Назначьте класс специализированным подам

В манифесте (Deployment, StatefulSet или Pod) специализированных подов явно укажите созданный низкий приоритет:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: specialized-worker
spec:
  template:
    spec:
      priorityClassName: low-priority-specialized # Явное указание
      containers:
      - name: worker
        image: specialized-image:latest
        resources:
          limits:
            cpu: "2"
            memory: 4Gi
          requests:
            cpu: "1"
            memory: 2Gi
```

Готовые манифесты из этой статьи — в репозитории [k8s-priority-eviction-autoscaling](https://github.com/patsevanton/k8s-priority-eviction-autoscaling): [priorityclasses.yaml](priorityclasses.yaml), [specialized-worker.yaml](manifests/specialized-worker.yaml), [critical-app.yaml](manifests/critical-app.yaml), [overprovisioning.yaml](manifests/overprovisioning.yaml) (placeholder-поды для второго паттерна).

## Демо: вытеснение в живом кластере

Теперь самое интересное — развернём кластер и спровоцируем вытеснение. Полный сценарий с командами и ожидаемым выводом — в [demo.md](demo.md), здесь — ключевые моменты.

### Стенд

Кластер Yandex Managed Kubernetes разворачивается одним `terraform apply` (инфраструктура — в [INFRASTRUCTURE.md](INFRASTRUCTURE.md)):

- одна маленькая нода 2 vCPU / 4 ГБ — чтобы исчерпать её было легко
- node group с `auto_scale { min = 1, max = 3 }` — это и есть включённый Cluster Autoscaler
- ноды без публичных IP, исходящий трафик через NAT-шлюз
- node group в одной зоне (`ru-central1-b`) — ограничение Yandex Managed K8s: авто-скейл-группы не могут быть мультизоновыми

Ключевой фрагмент Terraform:

```hcl
resource "yandex_kubernetes_node_group" "k8s_node_group" {
  # ...
  scale_policy {
    auto_scale {
      min     = 1 # Минимальное количество нод
      max     = 3 # Максимальное количество нод
      initial = 1 # Стартовое количество нод
    }
  }
}
```

В Yandex Managed K8s отдельная установка Cluster Autoscaler не нужна: `auto_scale` вместо `fixed_scale` — и платформа запускает управляемый автоскейлер.

### Шаг 1. Заполняем ноду низкоприоритетными подами

Применяем PriorityClass и запускаем 2 реплики specialized-worker, каждая с requests 900m CPU / 1.5Gi — вместе они почти полностью занимают ноду 2 vCPU:

```bash
kubectl apply -f priorityclasses.yaml
kubectl apply -f manifests/specialized-worker.yaml
```

```bash
$ kubectl get pods -o wide
NAME                                  READY   STATUS    NODE
specialized-worker-7d9f8b6c4-xk2p9   1/1     Running   cl1...-uxyz
specialized-worker-7d9f8b6c4-m4n8q   1/1     Running   cl1...-uxyz
```

Эти поды — те самые «специализированные нагрузки». Пока бизнес-приложений мало, они спокойно занимают ноду: вытеснять их некому, и они отрабатывают свои batch-задачи. Арифметика: из 2000m CPU ноды примерно 400m уходит на системные резервы kubelet, то есть подам доступно ~1600m — это и есть ~80 % ноды. Как только приходит критичное приложение с requests 900m, места не остаётся: 1600m + 900m > 2000m. Планировщик вытесняет низкоприоритетного воркера, тот уходит в Pending — и Cluster Autoscaler разворачивает вторую ноду уже под него.

### Шаг 2. Приходит критичное приложение

```bash
kubectl apply -f manifests/critical-app.yaml
```

У critical-app нет `priorityClassName` — он получает high-priority-default (1000000) через globalDefault. Но на ноде места уже нет: 2×900m + 900m > 2000m. Планировщик принимает решение о вытеснении:

```bash
$ kubectl get events --sort-by=.lastTimestamp | tail -6
LAST SEEN   TYPE     REASON      OBJECT                         MESSAGE
30s         Normal   Scheduled   pod/critical-app-5c8d7f...     Successfully assigned default/critical-app-5c8d7f...
45s         Normal   Preempted   pod/specialized-worker-...xk2p9 By default/critical-app-5c8d7f...
45s         Normal   Killing     pod/specialized-worker-...xk2p9 Stopping container pause
```

Событие `Preempted` с полем `By default/critical-app-...` — это и есть вытеснение в чистом виде: планировщик явно указал, кто и кого вытеснил.

### Шаг 3. Pending → новая нода

```bash
$ kubectl get pods
NAME                                  READY   STATUS    RESTARTS
critical-app-5c8d7f-9xz4l             1/1     Running          0
specialized-worker-7d9f8b6c4-m4n8q    1/1     Running          0
specialized-worker-7d9f8b6c4-xk2p9    0/1     Pending           0
```

critical-app занял место вытеснённого пода, а сам вытеснённый specialized-worker ушёл в Pending. Дальше в дело вступает Cluster Autoscaler — через 2–3 минуты в кластере появляется вторая нода:

```bash
$ kubectl get nodes
NAME                       STATUS   ROLES    AGE
cl1...-uxyz                Ready    <none>   18m
cl1...-uabc                Ready    <none>   47s   ← новая нода
```

И специализированный под запускается уже на ней:

```bash
$ kubectl get pods -o wide
NAME                                  READY   STATUS    NODE
critical-app-5c8d7f-9xz4l             1/1     Running   cl1...-uxyz
specialized-worker-7d9f8b6c4-m4n8q    1/1     Running   cl1...-uxyz
specialized-worker-7d9f8b6c4-xk2p9    1/1     Running   cl1...-uabc
```

Полный цикл замкнулся за пару минут без единого ручного действия: **нехватка → вытеснение → Pending → новая нода → все довольны**.

## Вариация паттерна: placeholder-поды для «тёплого» резерва (overprovisioning)

В демо выше низкоприоритетная нагрузка — это настоящие рабочие поды, которым просто не жалко подождать. Но ту же механику можно использовать и по-другому: вместо реальных воркеров запустить **placeholder-поды**, которые не делают ничего вообще. Это паттерн [node overprovisioning](https://kubernetes.io/docs/tasks/administer-cluster/node-overprovisioning/) из официальной документации, и он решает проблему холодного старта.

### Проблема: новая нода создаётся 2–3 минуты

Когда приходит пик нагрузки и места на нодах нет, новый под уходит в Pending и **ждёт**, пока Cluster Autoscaler развернёт ноду. В Yandex Managed K8s это 2–3 минуты, в других облаках — до 5–10 минут. Для нагрузки с жёсткими SLA это может быть неприемлемо: под за это время уже не успевает ни развернуться, ни прогреться.

Overprovisioning разворачивает проблему: мы **заранее** держим «тёплый» буфер мощностей, который занимает место при помощи ничего не делающих подов. В момент пика placeholder вытесняется за секунды — и реальный под стартует сразу, а не через минуты. Вытесненный placeholder уходит в Pending, автоскейлер добавляет ноду, и буфер восстанавливается сам.

```
   спокойный период                         пик нагрузки
   ┌────────────────────┐                  ┌────────────────────┐
   │ нода N1            │                  │ нода N1            │
   │ services + pause   │  pause вытеснен  │ services + NEW pod │
   │ placeholder        │ ───────────────► │   (запущен сразу)  │
   │ (держит резерв)    │                  └────────────────────┘
   └────────────────────┘                          │
              ▲                                    ▼
              │                          pause → Pending
              └── новая нода N2 ◄── Cluster Autoscaler
                  (буфер восстановлен)
```

### Настройка

Нужны PriorityClass с **отрицательным значением** и Deployment с минимальным pause-контейнером:

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: overprovisioning-placeholder
value: -1000
globalDefault: false
description: "Отрицательный приоритет для pause-подов резервирования мощностей"
```

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: overprovisioning
spec:
  replicas: 2 # Сколько буфера держим: replicas × requests
  selector:
    matchLabels:
      app: overprovisioning
  template:
    metadata:
      labels:
        app: overprovisioning
    spec:
      priorityClassName: overprovisioning-placeholder
      terminationGracePeriodSeconds: 0 # Резерв должен освобождаться мгновенно
      affinity:
        podAntiAffinity: # Раскидываем буфер по разным нодам
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  app: overprovisioning
              topologyKey: topology.kubernetes.io/hostname
      containers:
      - name: pause
        image: registry.k8s.io/pause:3.10 # Контейнер, который просто «спит»
        resources:
          requests:
            cpu: 900m # Размер резерва, который держит один placeholder
            memory: 1.5Gi
```

Ключевые детали:

- **`value: -1000`.** Отрицательный приоритет гарантирует, что placeholder будет первой жертвой вытеснения — ниже него только ничего не значащие поды без класса. Интересный эффект: поды без `priorityClassName` получают приоритет **0**, то есть уже выше placeholder'ов. В минимальной конфигурации (только placeholder'ы и обычные поды) `globalDefault` из первого паттерна вообще не обязателен.
- **`requests` — это и есть размер резерва.** Pause-контейнер потребляет копейки; placeholder «занимает» ровно столько, сколько заявлено в `resources.requests`. Общий буфер = `replicas × requests`. Готовый манифест для демо-стенда — [manifests/overprovisioning.yaml](manifests/overprovisioning.yaml).
- **`terminationGracePeriodSeconds: 0`.** Стандартные 30 секунд graceful shutdown — это 30 секунд задержки перед тем, как место освободится. Placeholder нечего «корректно завершать», поэтому выключаем ожидание.
- **Pod anti-affinity** (`preferredDuringSchedulingIgnoredDuringExecution` по hostname) — «мягкое» правило, старающееся распределить placeholder-поды по разным нодам. Без него весь буфер может осесть на одной ноде — и при её сбое вы теряете весь резерв разом.

### requests запускает масштабирование, priority разрешает вытеснение

Здесь легко запутаться, поэтому разделим роли явно:

- **`resources.requests` placeholder-пода — триггер scale-up.** Приоритет сам по себе не заставляет Cluster Autoscaler ничего делать: автоскейлер реагирует только на поды в состоянии `Unschedulable` из-за нехватки ресурсов. Placeholder с requests 900m, который не помещается, — это и есть сигнал «нужна нода».
- **Отрицательный `priority` — включатель мгновенного вытеснения.** Он гарантирует, что занятый placeholder'ом объём будет отдан новому поду немедленно, без ожидания.

### Trade-off: вы платите за скорость

Placeholder-поды не бесплатны: буфер — это простаивающие мощности, за которые идёт обычная оплата. Взамен вы покупаете скорость реакции кластера: секунды вместо минут. Паттерн окупается при непредсказуемых всплесках с жёсткими требованиями к времени развёртывания; при плавной предсказуемой нагрузке дешевле полагаться на обычный реактивный автоскейлинг.

> Нюанс для других облаков: [Karpenter](https://karpenter.sh/) трактует `preferred` anti-affinity как жёсткое ограничение при масштабировании — число реплик placeholder-Deployment задаёт тем самым минимальное число нод. Классический Cluster Autoscaler (и Yandex Managed K8s) так не делает: для него anti-affinity — только предпочтение при размещении.

## Важные нюансы для корректной работы

**Настройка Cluster Autoscaler.** Убедитесь, что у вас включён автоскейлинг нод. Когда специализированные поды уйдут в Pending, Autoscaler увидит нехватку ресурсов для подов с приоритетом 1000 и начнёт создавать новую ноду. В Yandex Managed K8s это делается через `auto_scale` в node group; в self-hosted — установкой Cluster Autoscaler с явным указанием минимального и максимального размера групп нод.

**Запросы ресурсов (Requests).** Вытеснение сработает только в том случае, если у ваших подов чётко прописаны `resources.requests`. Kubernetes сравнивает приоритеты только тогда, когда физически не может разместить под из-за нехватки запрошенных ресурсов. Под без requests для планировщика «весит ноль» — он не вытеснит никого и сам не станет причиной масштабирования. Это самая частая причина, почему приоритеты «не работают». Полезно запомнить разделение ролей: **requests — триггер масштабирования, priority — право вытеснять**. Приоритет сам по себе не заставляет Cluster Autoscaler создавать ноды — тот реагирует только на поды в состоянии `Unschedulable` из-за нехватки ресурсов.

**Диапазон значений и имена PriorityClass.** Значение `value` — 32-битное целое от -2147483648 до 1000000000; всё, что выше миллиарда, зарезервировано за встроенными системными классами (`system-cluster-critical` = 2000000000, `system-node-critical` = 2000001000). Имя класса должно быть валидным DNS-именем и не может начинаться с префикса `system-`. Отрицательные значения — не хак, а штатный механизм, официально используемый для placeholder-подов.

**globalDefault не влияет на существующие поды.** Приоритет из класса с `globalDefault: true` присваивается только подам, созданным **после** появления класса. Если вы внедряете паттерн в живой кластер, уже запущенные поды свой приоритет не пересчитают — их приоритет останется прежним (0, если классов не было). Рестарт подов после применения PriorityClass — на совести деплой-пайплайнов.

**Защита от циклического перезапуска (Flapping).** Если новая нода создаётся слишком долго, специализированные поды будут находиться в Pending. Как только нода поднимется, они запустятся там. Убедитесь, что лимиты автоскейлера позволяют расширять кластер (`max` в auto_scale не должен упираться в квоту облака), и что развертывание подов не блокируется чем-то ещё — например, лимитами namespace (ResourceQuota) или отсутствием доступа к реестру образов.

**Политика вытеснения.** По умолчанию свойство `preemptionPolicy` в PriorityClass имеет значение `PreemptLowerPriority`. Это именно то, что вам нужно (высокий вытесняет низкий). Альтернативное значение `Never` означает, что под с таким классом не будет вытеснять других — он честно ждёт в Pending, пока место не освободится, но при этом стоит в очереди планирования впереди низкоприоритетных. Это полезно для подов, которым самому «неудобно» кого-то тревожить (типичный пример — data science задачи: высокий приоритет в очереди, но без разрушения чужой работы), но для нашего паттерна нужен именно дефолт.

**Graceful shutdown.** Вытеснение — это обычное удаление пода с соблюдением `terminationGracePeriodSeconds` и preStop-хуков. Значение по умолчанию — 30 секунд, и всё это время место на ноде считается занятым: между вытеснением жертвы и запуском вытесняющего пода есть пауза. Если ваши специализированные поды обрабатывают длинные задачи, позаботьтесь о том, чтобы они корректно завершали работу: проверяли SIGTERM, сохраняли прогресс, ставили чекпоинты. Иначе каждая волна вытеснений будет обрывать работу на середине. А для placeholder-подов graceful shutdown не нужен вовсе — там ставят `terminationGracePeriodSeconds: 0`, чтобы резерв освобождался мгновенно.

**PodDisruptionBudget — best effort.** Планировщик старается не нарушать PDB при выборе жертв, но если жертв без нарушения PDB нет — вытеснение всё равно произойдёт. Не рассчитывайте на PDB как на защиту от приоритетного вытеснения: он ограничивает добровольные disruptions (drain, вытеснения при обновлениях), а не scheduler preemption.

**Inter-pod affinity — только к равным или более высоким приоритетам.** Нода рассматривается как кандидат на вытеснение, только если удаление с неё всех низкоприоритетных подов позволило бы разместить новичка. Если у вытесняющего пода есть affinity к низкоприоритетному поду, то после удаления «жертвы» правило перестанет выполняться — и планировщик просто не станет трогать эту ноду.

**Мульти-тенантность: приоритеты как объект атаки.** В кластере, где поды создают не только доверенные команды, пользователь может создать под с максимально высоким приоритетом и начать вытеснять чужие нагрузки. Защита — ResourceQuota с ограничением потребления PriorityClass ([scopeSelector по priorityClassName](https://kubernetes.io/docs/concepts/policy/resource-quotas/)): например, квотой, разрешающей использовать `high-priority-default` только в системных namespace.

**Не путайте с eviction под давлением.** PriorityClass также влияет на порядок, в котором kubelet выселяет поды при нехватке памяти на ноде (node-pressure eviction) — но это другой механизм с другими причинами. Причём kubelet ранжирует поды иначе: сначала — превышение requests по дефицитному ресурсу, только потом — приоритет, и не трогает поды, потребляющие в рамках requests, даже низкоприоритетные. QoS-класс пода в вытеснении планировщиком вообще не участвует. В этой статье речь о вытеснении планировщиком (scheduler preemption), которое происходит из-за нехватки места именно для нового пода.

## Когда этот паттерн уместен

Паттерн «низкоприоритетные поды + автоскейлинг» особенно хорош, когда у вас есть нагрузка, которая **может подождать**: batch-обработка данных, CI/CD-раннеры, ML-эксперименты, репликация/синхронизация, прогрев кешей. Такую нагрузку можно спокойно пускать на «остатках» кластера — а когда приходят критичные сервисы, они не встают в очередь за свободными мощностями, а забирают их себе. Важно понимать, за что именно вы платите: простаивающие standby-мощности стоят обычных денег, даже когда работают только pause-поды. Взамен — скорость: вытеснение placeholder'а и запуск на его месте реального пода занимает секунды, тогда как создание ноды в облаке — минуты.

Overprovisioning через placeholder-поды — это про покупку скорости за деньги: он окупается при непредсказуемых всплесках с жёсткими SLA (flash sales, продакшен с дорогим простоем), и избыточен при предсказуемой нагрузке, где обычного реактивного автоскейлинга достаточно.

Обратная сторона: если низкоприоритетная нагрузка занимает ноды, а автоскейлер по какой-то причине не может расширить кластер (квота, лимит max, недоступность зон), вытесненные поды будут ждать в Pending неограниченно долго. Приоритеты — не замена мониторингу: алерт на долго живущие Pending-поды и на не расширяющиеся node groups должен быть в любом случае.

## Итоги

Мы развернули в Yandex Managed Kubernetes кластер с автоскейлингом, настроили PriorityClass — высокий дефолтный через `globalDefault`, низкий для специализированных подов и отрицательный для placeholder'ов — и пронаблюдали полный цикл: критичное приложение вытеснило низкоприоритетного воркера, воркер ушёл в Pending, Cluster Autoscaler добавил ноду, и все поды продолжили работу. Тот же механизм в вариации с placeholder-подами даёт «тёплый» резерв: ноды под будущий пик разворачиваются заранее, а при всплеске место освобождается за секунды.
